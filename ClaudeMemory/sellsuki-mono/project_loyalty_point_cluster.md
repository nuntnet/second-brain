**Loyalty point cluster under epic OC-2743 (Point Budgeting Management) — designs locked with user 2026-07-08/09.** Engine facts (3rdparty-api = real engine, campaign-engine repo = empty shell, reward = fixed Quantity only) are in [[reference_oc2plus_member_frontend]].

The 5-card map and key locked decisions:
- **OC-4295** (point ตามยอดซื้อ): purchase system event under existing campaign engine + per-campaign conversion config "ทุกๆ X บาท = Y point" → `quantity = floor(amount/X)` through existing engine path; rounding = floor per bill; overlap policy v1 = **award ALL eligible campaigns** (no priority/exclusive; warning at create, never block); rate field lives in shared entity module → version bump BO + 3rdparty together.
- **OC-4297** (welcome → **welcome/acquisition reward**, expanded 2026-08-05): reward from **event** (register OR line-link), reward = **point และ/หรือ product** (not point-only). **4 selectable scenarios** = trigger + attribution filter + reward: (1) register any-channel [core, no filter] (2) member links LINE first time → needs new `LINE_LINK` event; **emit point = OC-4245 phone+OTP flow, branch where existing member matched-by-phone + gains line identity for the FIRST time (was-empty→now-set); distinct branch from fresh-insert/scenario 1; NOT on repeat OTP login of already-linked member** (3) register via special QR/link OR time-window only → register must carry **attribution/source** + campaign filters on it (4) register via receipt-QR → stack OC-4297 welcome + OC-4335 purchase; **scenario 4 blocked-by OC-4335 (purchase half, OC-4297 doesn't do it) + receipt-QR gen (Layer B, POS/Patona); scenarios 1-3 do NOT depend on OC-4335**. **Legacy martech precedent (code team, OC2Plus currently has NONE):** welcome was a hardcoded single code `7QFIRYG3B7G5K53X` → auto-redeem code-campaign post-register → award point/product. Key insight: "hardcode code" = special case of attribution-filter=code, so event+filter model subsumes it. Gaps: seed REGISTER+LINE_LINK system events (event Type column dead — event_repository/postgresql.go:314-329), emit member.created at use-case level in TWO places (member_liff.go:174 new / member.go:138 old; repo can't distinguish new/existing due to ON CONFLICT DO NOTHING), add attribution/source to member+payload (none today), attribution filter on campaign (engine+BO), idempotency = LimitUsagePerMember=1 is TOCTOU-racy → DB unique (member_id, campaign_id).
- **OC-4335** (QR ท้ายใบเสร็จ, 2 โหมด): mode A fixed = reuse existing code-gen lots (works offline, POS batch-pulls codes); mode B by-amount = **pull model per user's proposal**: one-time code bound to order serial only (no amount baked in) → at claim, validate code → call Patona order-lookup API {amount, status, purchased_at} → compute → consume(CAS)+award in one txn. Rate = campaign active at **purchased_at** (decision closed). Fetch-before-consume so OMS downtime never burns the code. Dedup across paths = unique order serial shared with OC-4295 auto-award. Integration: OC2Plus provides code APIs on 3rdparty-api (API-key infra exists), Patona = requester → POS work is a PAT-board card (contract written in OC-4335); open decision: code↔serial binding = async registration (recommended) vs HMAC-signed serial.
- **OC-4339** (clawback): order cancelled/refunded AFTER award → compensating deduction found via order-serial attribution; needs new activity type `revoke` (enum today = earn|redeem|expire only) in shared entity module; open business decisions: negative balance vs floor-0 (recommended: allow negative), partial refund pro-rata, welcome point NOT clawed back.
- **OC-4362** (ใบเสร็จ**ไม่มี QR**): member กรอก receipt_number+amount+date+photo → **admin manual review** (no OCR v1) → approve = award via **campaign engine (like OC-4295), NOT adjust-point** (attributed earn source=campaign, rate ณ purchase_date); dedup = unique(company_id, receipt_number) for pending/approved + rate-limit 5/day + atomic state guard; no active campaign ณ date → auto-reject (OC-4294 = exception path only).
- **OC-4335 rev 2026-08-06:** mint = **open API OC2Plus, ไม่ผูก Patona** (any printer/3rd-party via API key); returns **code + claim_url string, NOT a QR image** (consumer renders QR; optional qr.svg helper only; never backend image gen). Mode B mint = **3 strategies**: live / **preload+async-bind (OC2Plus issues unbound lot → POS binds serial via async registration; receipt_codes.order_serial nullable; claim-before-bind = "รอสักครู่")** / signed-serial. order-lookup = per order-source (Patona OR 3rd-party's own order API); mode B needs order-lookup else fallback mode A. Claim URL carries code; claim needs member identity first via 3 paths (LINE session / browser member-login / register), code carried through the identity step. Admin UX (setup campaign → Code Lot page → export CSV vs open API) pinned as comment.
- **OC-4294** = manual adjust (interim/fallback). **Not used for receipt/marketplace point-award** — those go through campaign engine; OC-4294 only for exceptions (no active campaign).
- **Channel matrix "แต้มตามยอดซื้อ" = 1 engine (OC-4295 conversion, rate ณ purchased_at), differs only in amount-source + verify + dedup-key:** POS-auto (order event / system / order-serial / OC-4295) · QR-receipt (order-lookup / system / order-serial / OC-4335) · no-QR-receipt (member-entered+photo / admin review / receipt_number / OC-4362) · **Marketplace Shopee-Lazada-TikTok (NO card yet — proposed): connector-pull by marketplace_order_id (Patona/Akita already has connectors; if OMS ingests mp orders → reuse OC-4335 pull-model, order-source=marketplace) OR member-enter mp_order_id+screenshot+review (OC-4362 pattern); key risk = identity matching (marketplace buyer ≠ member); dedup = marketplace_order_id**.

**Design-driven enhancement 2026-08-07** (source: "CRM Loyalty campaign prototype.zip" — Create Campaign.dc.html + Purchase Product.dc.html; the claude.ai share link 403s, the ZIP is the usable artifact). New campaign type **"Purchase product"** joins existing (กรอกโค้ด / ร่วมกิจกรรม / ใช้คะแนน); wizard = รายละเอียด→ประเภท→เงื่อนไข→รางวัล. **NEW business reqs folded into cards:** (a) **3 exclusive reward modes** — `multiplier` x2/x3 **over a store-level base rate** · `flat_per_receipt` (ซื้อครบ X = Y แต้ม, doesn't scale) · `campaign_rate` (ทุก X บาท = Y แต้ม, the legacy one); (b) **product scope** all vs selected SKU/category → **engine needs LINE ITEMS not just total** (contract change for every adapter; no line items + scope=selected ⇒ skip, never fallback to total); (c) **count_mode** per_receipt vs **cumulative** (stateful running total per member×campaign); (d) **rounding** floor/ceil/nearest (was hardcoded floor); (e) **caps** per-receipt + per-member; (f) **eligibility** all/new-member/tier-segment; (g) **channel filter** LINE OA/store/web; (h) member **limit per campaign/day/month** (was per-campaign only); (i) **point unit** Point/Coin/Stamp (units already exist: OC-3505/3716); (j) wizard extras — image 1200×630, 8 categories, auto-publish-on-start-date, **preset templates A/B/C**; (k) product reward = qty + pickup-within-N-days | shipping free/fee; (l) **coupon reward = explicitly deferred** (needs Coupon master). **New card OC-4415 = Base Earn Rate** (store-level "25 บาท = 1 แต้ม" that multiplier mode multiplies; did NOT exist — OC-2380 is budgeting/limit, different thing); blocks OC-4295 + OC-4413; open decision: always-on (earn on every purchase) vs reference-only. **Code-verified invariants 2026-08-07** (repos are on disk: `backend/oc2plus-line-crm-service-{3rdparty,backoffice,member}-api`; codegraph MCP was down, grepped directly): (1) **NO base earn rate exists** — `entity@v1.7.3/point.Point` = `{PointID, Name, Icon, Status, Description, IsPrimary, timestamps}`, no rate/exchange field (but `IsPrimary` exists = design's "Point หน่วยหลักของร้าน"). (2) **EVERY award path is wrapped by a campaign — there is no award primitive outside campaign:** v1 `/campaign/{campaign_code}/confirm`, v1 `/campaign/code/confirm`, v2 `/campaign/event/confirm` whose `EventConfirmRequest` requires `event_code + campaign_code + member_id` and **has no amount field**. Specs live at `3rdparty-api/src/interface/fiber_server/spec/{v1,v2_openapi}.yaml`. → **Consequence: if base-rate is "always-on", implement it as an implicit/system campaign (SYSTEM_BASE_EARN, seeded per company, hidden from list, edited via Base Earn Rate page) rather than a new non-campaign award path** — preserves "every point has campaign attribution", reuses dedup/limit/expiry/audit/clawback, needs zero contract changes. Side effect to settle: base campaign stacks with an x2 campaign under the existing award-all-eligible policy (⇒ 3x, not 2x) — must decide whether multiplier mode suppresses base or awards only the delta.

**Config-hub model (settled 2026-08-07):** **OC-4295 is the single place that defines "how many points"** (scope/threshold/count-mode/reward-mode/rounding/caps/eligibility/channel/point-unit/limits) for EVERY amount-based channel — POS-auto (4414), POS-sync (4412), QR-receipt mode B (4335), no-QR receipt (4362), marketplace (4407). Those cards only define "where the amount comes from and how it's trusted". **Exception: QR-receipt mode A (fixed points) is a different campaign type ("กรอกโค้ด"/code-gen), configured elsewhere.** Gap found & logged: `channel` enum lacked **marketplace** (design had only all/line_oa/store/web) → must add. Keep `channel` (where bought) separate from "how points were claimed" (auto/scan/manual) — the latter is NOT a v1 filter. **QR-receipt = pull model: no scan ⇒ no points, expires ~30d.** Its reason for existing = **anonymous purchase** (member unknown at checkout); if the member IS identified at checkout, auto-award via Kafka/sync happens and the QR is redundant — cross-path dedup on `(company, order_ref)` blocks the double, and the UI must say "ใบเสร็จนี้ได้รับแต้มแล้ว" rather than erroring.

**POS↔CRM identity + product-scope limits (verified 2026-08-07):** (1) **v2 openapi accepts only `member_id` (UUID), no phone field and no lookup-by-phone endpoint** → cashiers can't use it → decided: purchase-award must accept `member_ref` as **phone E.164 (primary)** / member-QR token / member_id; phone is already the member identity key (v1 `/me/phone/request`+`/me/phone/update` OTP-verified; OC-4362 calls it identity key). Guards: E.164 normalize, rate-limit anti-enumeration, no PII in response. (2) **Products are NOT owned by CRM — backoffice-api reads PIS over REST** (`product_repository/rest.go`: `GET {BaseURL}/products`, `/products/{id}/refID/{refId}`), model `Product{ID,Code,Name,Price,Variant[].Sku}` — so the product picker needs **no new sync**, it's a live read. (3) **Product-scope campaigns have hard channel limits:** they only work where line_items exist — sync API yes; Kafka unconfirmed (ask PAT); **no-QR receipt (4362) and marketplace-manual (4407) can NEVER work** (member enters only a total) → UI must warn before save. Also needs SKU alignment between POS line_items and PIS, product-name snapshot at campaign creation (so deleted products still render), and category membership resolved live at purchased_at. (4) **Receipt-QR TTL is a company-level setting `receipt_code_ttl_days` (default 30, 1–180), not per campaign** (a code is minted per order and may match several campaigns); mint API must return `expires_at` so the printer can print "สแกนภายใน DD/MM". (5) QR-receipt's raison d'être stated explicitly: **the POS has no field to capture phone/member at checkout**, so identity is unknown and API award is impossible.

**Resolved design decisions (2026-08-07, now spec in OC-4295/4413/4415):** multiplier = **เบ็ดเสร็จ/suppress base** (x2 ⇒ 2× total not 3×; base still applies to the non-eligible portion when scope=selected) · **multiplier dropdown x2–x10** (design had only x2/x3) + **must display current base rate + live preview + say "เบ็ดเสร็จ ไม่ใช่ส่วนเพิ่ม"** · flat-per-receipt locks count_mode=per_receipt · min-amount computed on **eligible** amount · cumulative hides per-receipt cap · dedupe the duplicated fields (member-limit → participation section; point-unit & expiry → calculation section) · ceil rounding requires a min-amount · **overlapping multiplier campaigns use the highest single one, never additive** · product reward hides the 3 point modes · drop "สะสมแต้ม" from the category list · presets don't prefill dates.

**Prototype logic gaps found in design review (2026-08-07, logged as comment on OC-4295):** ตัวคูณ+base double-count · flat-per-receipt vs cumulative conflict · min-amount computed on whole bill vs eligible-only (ambiguous) · per-receipt cap under cumulative · **duplicate fields rendered twice with no v-if in the prototype** (จำกัดการใช้ของสมาชิก in both เงื่อนไขการเข้าร่วม & เงื่อนไขการซื้อ; หน่วยแต้ม + วันหมดอายุ in both fixed-amount and calculation blocks) · ceil rounding = free-points exploit (1฿→1pt) · overlapping multipliers compound (x2+x3 = 5x) · product-reward vs the 3 point-modes undefined · campaign category list mixes two taxonomies · presets hardcode 1–31 ส.ค.

**Sync purchase-award gap → OC-4412 (created 2026-08-06):** OC-4295's runtime (Flow C) is **async Kafka only** (purchase activity from OC-4286/4287 → connector → award; blocked-by activity ingestion). Engine EventConfirm = fixed-qty, no amount/conversion/order-dedup. **Missing = a synchronous open API where POS/ERP fires `{member_ref, order_id, amount}` directly → 3rd-party runs campaign logic inline (conversion floor / threshold / order-id dedup / limit / active window) → award + returns points in the response.** OC-4412 fills it (reuses OC-4295 conversion + engine award; adds POST /v2/openapi/purchase-award + order_id idempotency shared cross-path with OC-4295/4335 + threshold field + member resolution). Open decisions: member_ref shape (id/phone/member-QR), threshold home (entity shared w/ OC-4295), no-active-campaign policy (200 award-0 vs error). Note: **threshold (min purchase amount) is a general gap — OC-4295 only has floor(amount/X), no explicit min-spend threshold.**
